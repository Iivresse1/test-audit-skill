Q4：静态初筛与 Red Proof

目标：理解代码审查能提出什么怀疑，以及一次有针对性的失败实验能增加什么证据。

一句话：静态审计分析预言机的来源；动态验证检查测试能否识别某一类真实错误。两者都不能单独证明测试套件“完整”。

先修正一个容易混淆的例子

// A: 具体需求示例
expect(add(2, 3)).toBe(5);

// B: 镜像公式
expect(add(2, 3)).toBe(2 + 3);

// C: 真正的数据循环
const expected = add(2, 3);
expect(add(2, 3)).toBe(expected);

A 的预言机最清楚。B 与实现可能共享“加法”这一解释，因此有相关性风险，但它仍会在生产代码把 + 改为 - 时失败。C 的 expected 来自被测函数本身，除非函数不确定或有副作用，否则它几乎只是在证明同一次计算等于自己。

所以，“测试里出现了同样的公式”不等于“测试必然同义反复”。审计器需要追踪 expected 的来源，并说明该来源和实现共享了什么假设。

静态审计能做什么

  1. 追踪 actual 与 expected 的数据来源。
  2. 识别生产 helper、共享 fixture、mock 配置和复制算法。
  3. 比较断言与规格：它验证结果、持久化状态、副作用，还是只验证调用发生。
  4. 提出一个具体假设：“如果这里把边界条件改错，这个测试可能仍然通过。”

静态结果应写成“疑似问题 + 共享依赖 + 可能漏掉的错误”，而不是只给一个标签。测试预言机本身就是软件测试中的独立难题；规格、契约、模型、变形关系和人工判断都可能成为预言机来源。1

Red Proof 是什么

Red proof 是一个小型反事实实验：暂时引入一个与需求相关的错误，然后运行目标测试，看它会不会变红。Mutation testing 将被测试捕获的变异称为 killed，将所有测试仍通过的变异称为 survived。2

// 原实现
return a + b;

// 定向变异：模拟错误运算符
return a - b;
结果可以说明不能说明
测试失败该测试能识别这个具体错误模型不能证明它覆盖所有需求或错误
测试仍通过该错误没有被当前测试观察到不能自动证明测试同义反复

为什么 survived 不是自动定罪？

  • 变异可能与原程序语义等价，因此没有任何测试能够区分。
  • 变异可能不属于该测试声称负责的行为。
  • 错误可能被更高层测试捕获，而不是当前单元测试。
  • 测试可能覆盖执行路径，却缺少能观察变化的断言。

PIT 明确提醒存在等价变异；Microsoft 的实践文档也不建议追求 100% mutation score。34

给审计 Skill 的决策规则

  1. 先基于规格和风险定义该测试声称保护的行为。
  2. 静态追踪 expected 的来源，给出初步分类和置信度。
  3. 只有高价值且安全可变异的行为才执行 red proof。
  4. 把 survived 解释为“这个错误模型未被检测”，再调查原因。
  5. 仅当 expected 与 actual 存在循环依赖时，直接标记循环预言机。

快速检索练习

先在脑中回答，再展开答案。

expect(add(2, 3)).toBe(2 + 3) 是严格同义反复吗？

不是。它是镜像公式，存在共享需求解释的风险，但仍能杀死“加号变减号”等变异。

某数据库回滚测试只断言 API 返回 500，足够吗？

不足。它覆盖了错误响应，却没有验证事务回滚后的持久化状态、关联记录和后续读取，因此是覆盖范围与预言机强度问题，不一定是同义反复。

一个变异 survived，能否直接删除该测试？

不能。先判断变异是否等价、是否属于该测试职责，以及缺陷是无覆盖、弱断言、错误隔离，还是循环预言机。
